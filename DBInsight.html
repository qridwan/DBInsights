A hybrid static and runtime analysis framework for ORM-based applications

Detecting database performance and data-quality problems by correlating evidence across application source code, the ORM layer, generated SQL, schema metadata, runtime query behaviour, and the data itself — then measuring whether that correlation actually helps.

The contribution is the correlation and its measurement, not any single detection technique. N+1 detection, index advice and query fingerprinting all exist in shipping tools. What does not exist is a controlled measurement of whether combining five evidence layers detects more, and more reliably, than any one of them alone.
01 — Why now

The gap is real, and one vendor just vacated it

Existing tools sit on one side of the application-to-database boundary or the other. None reason across it, and the ORM vendor that tried abandoned the attempt in March 2026.

Prisma Optimize

Shipped almost this exact feature set, then sunset in March 2026. The published post-mortem names a client extension for monitoring as the primary adoption blocker. Its replacement is tied to Prisma's own hosted Postgres.

pganalyze

Mature Postgres-side index advisor with enterprise deployments. Its own documentation concedes the boundary problem: slow queries can be hidden by ORM calls in application code.

Scout APM

Runtime N+1 detection for Prisma by instrumenting the query engine. Grounded in real behaviour, but reasons about neither schema nor data distribution.

Reformulator · ASE 2022

Static data-flow analysis that automatically refactors N+1 patterns in Sequelize. Proves the technique is viable — and marks remediation as territory this project deliberately does not enter.

Positioning follows from this. The project claims no novelty in N+1 detection, index recommendation, query fingerprinting or anomaly detection. Each already exists. The claim is the multi-layer correlation, the controlled comparison of evidence configurations, and the measurement of how much is achievable without a database connection at all.
02 — Research questions

Six questions, one of them new to this revision

RQ1
How effectively can a hybrid static and runtime framework detect database performance and data-quality problems in ORM-based applications?
RQ2
Does ORM-aware source analysis detect problems that SQL analysis alone misses?
RQ3
Does combining static analysis with runtime behaviour improve precision and recall?
RQ4
Can statistical anomaly detection identify unexpected changes in query behaviour and data characteristics?
RQ5
What trade-offs exist between detection accuracy, false positives, and analysis overhead?
RQ6
To what extent does an ORM's declared schema diverge from the database's actual schema, and what does that divergence cost findings derived from the declared schema alone?new

Hypotheses

H1
Hybrid analysis detects a broader range of issues than static SQL analysis alone.
H2
ORM-aware analysis improves detection of application-level anti-patterns such as N+1.
H3
Runtime analysis provides stronger evidence for performance findings than static analysis alone.
H4
Statistical anomaly detection identifies meaningful changes in query behaviour and data distributions.
H5
A substantial share of index findings obtainable from the live database are also obtainable from the declared schema alone — making them available with no database connection.new
03 — Method

Evidence configurations, ordered by what they cost to obtain

The three approaches differ in which evidence sources each may use. They are ordered deliberately by operational cost, so the comparison answers a practical question and not only a methodological one.

Approach A — Static SQL

Raw SQL through the SQL analyzer. No ORM source, no schema, no database.

Baseline

Approach B — Static source + declared schema

ORM source, raw SQL and schema.prisma through the static analyzers. Everything already present in a source repository.

Repository read access only · no database, no instrumentation

Approach C — Hybrid

Everything in B, plus live information_schema metadata, runtime query behaviour and data-quality statistics, merged by the correlation engine.

Database credentials + production instrumentation

The B/C boundary is the central design decision

The ORM's schema file is a static source artifact, but it encodes declared indexes, relations and field types — information prior work treats as inherently database-side. In ORM projects it is partly recoverable from source. Approach B is constructed to measure exactly how much, which is why the experiment runs as a six-configuration ablation rather than three coarse buckets.

Ground truth and measurement

Two purpose-built Prisma/PostgreSQL applications — e-commerce and blog/CMS — carry deliberately injected problems recorded in a machine-readable manifest. Purpose-built applications are used because precision and recall require the ground truth to be fully known. A separate real-world validation study (M6) compensates for the external-validity cost.

04 — Architecture

Two boundaries define the system

One separates evidence that costs nothing to obtain from evidence that requires privileged access. The other separates everything measured from the generated text that is not.

The AI layer sits outside the evaluation by construction. It receives an already-scored finding and returns prose; it cannot change whether that finding is a true positive, so it contributes no data to precision, recall or F1 — and the detection results stay reproducible regardless of model variability.

05 — Plan

Milestones with exit criteria, not a calendar

A milestone completes when its criteria are met. No milestone starts before its dependency exits, and every milestone has a written fallback decided before it begins rather than after it goes wrong.

M0

Foundations

depends on — nothing

Literature review finalised with verified citations. Repository, core package skeleton, CI. Two test applications adapted from open-source Prisma starters.

Exit
  • No unverified citations remain
  • Both apps run from one compose command
  • Core package builds and tests in CI
M1

Static core + declared schema

depends on — M0

Schema parser, ts-morph ORM analyzer with data-flow resolution, SQL analyzer. Rules emitting findings with confidence and evidence.

Exit
  • Accepts any source directory — zero test-app-specific logic
  • Distinguishes a loop over an ORM result from a loop over a literal
  • Zero findings on both apps before injection
M2

Ground truth injection

depends on — M0 · parallel to M1

Injected performance, data-quality and schema-divergence problems, each recorded in a machine-readable manifest keyed to file and line.

Exit
  • Manifest drives scoring automatically — no manual tallying
  • Every problem reachable through an HTTP endpoint
  • Three or more instances per problem type
  • Divergence cases in both directions
M3

Runtime + actual schema

depends on — M1, M2

Prisma event collector, query fingerprinting, per-request repetition counting, information_schema reader, reproducible load harness.

Exit
  • Fingerprinting survives the ORM over-granularity failure mode
  • Load harness repeatable within ~5% variance
  • Collector overhead measured — this is RQ5 data
M4

Data quality, anomaly, correlation

depends on — M3

Data profiler, anomaly detector against learned baselines, and the correlation engine merging all five evidence layers into scored findings.

Exit
  • Baselines learned, not fixed thresholds
  • Correlation demonstrably changes a verdict
  • Confidence scores reproducible across runs
M5

Controlled experiment + ablation

depends on — M4

All six configurations against both applications with repetition, then statistical analysis of the pairwise comparisons that answer RQ3 and RQ6.

Exit
  • Ten or more repetitions per configuration
  • Means with confidence intervals, not single runs
  • Significance testing on B2 vs C1 and C1 vs C2
  • Per-problem-type breakdown
  • Reproducible from one command
M6

Real-world validation

depends on — M1 only · runs in parallel

Approach B run against 15–20 open-source Prisma projects, every finding manually labelled, real-world precision computed per rule.

Exit
  • 15+ repositories on a stated selection criterion
  • Labelling protocol written before labelling starts
  • Second labeller on 20%, Cohen's kappa reported
  • Divergence frequency documented in real projects
M7

Adapter generalisation

depends on — M5 · optional, first to cut

MySQL adapter and Drizzle adapter, with a reduced experiment on one new combination — demonstrating the adapter claim rather than asserting it.

Exit
  • Second database works without core changes
  • Second ORM works without rule changes
  • Differences from the baseline discussed
M8

Dashboard, AI layer, write-up

depends on — M5

Next.js dashboard, the evidence-consuming AI explanation layer, the thesis document and defense materials.

Exit
  • End-to-end scenario demonstrable in under five minutes
  • AI layer verified unable to alter severity or confidence
  • All six research questions answered against specific results
  • Threats to validity written honestly
M6 is the argument for the extended timeline. M5 shows the tool finds problems that were deliberately planted. M6 shows whether it works on code written by people who were not trying to create any. Those are different claims, and only the second predicts how the tool behaves outside the experiment. Because M6 depends on M1 alone, it runs alongside M3 through M5 instead of extending the critical path.
06 — Scope

What this project does not claim

  • Scoped to one ORM and one database. The adapter architecture is designed for more; implementing them is optional and not part of the core claim.
  • Test applications are purpose-built rather than production systems. This trades external validity for measurement control — the cost M6 exists to offset.
  • The AI layer never determines a finding's type, severity or confidence, and is excluded entirely from the quantitative evaluation.
  • Detection is probabilistic by design. Static findings raise suspicion; runtime and schema evidence strengthen or weaken confidence. Nothing is presented as certain without supporting evidence.
  • Autonomous remediation is out of scope. Reformulator already refactors N+1 patterns automatically, and competing there would be a poor use of the time available.
  • A negative or mixed result is a valid outcome. If the hybrid approach improves recall only for some problem types, or at overhead that makes continuous operation impractical, that is the finding and it gets reported as one.
